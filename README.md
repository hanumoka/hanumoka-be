# hanumoka-be

**Spring Boot · Kotlin · JPA 멀티모듈에 공통 핵심 도메인을 하나씩 붙여 가는 프로젝트입니다.**

이벤트 시스템, 분산락, 캐싱, 계정계 같은 것들을 **직접 만들고 재 보면서** 각각이 왜 그렇게 생겼는지 이해하는 것이 목적입니다.

## 만드는 방식

### 1. 실패를 먼저 봅니다

**완성형으로 만들지 않습니다.** 일부러 깨진 상태로 시작해서 문제를 하나씩 만나며 고칩니다.

*"먼저 단순하게 만들었더니 유실이 났고, 그래서 Outbox를 넣었고, 그랬더니 중복이 나서 멱등을 넣었다"* —
**이 순서를 기록으로 남기는 것이 완성된 코드를 보여주는 것보다 낫다고 생각합니다.**

각 단계마다 넷을 남깁니다.

- 무엇이 깨졌나
- 왜 깨졌나
- 어떻게 고쳤나
- **그때 잰 값**

### 2. 모듈마다 잽니다

**모듈을 하나 추가할 때마다 처리량·지연·병목을 재서 기록합니다.**

나중에 몰아서 재려고 하면 안 하게 되므로 규칙으로 둡니다. 측정 조건(도구·환경·부하)을 값과 함께 적습니다 — **조건 없는 수치는 수치가 아니기 때문입니다.**

## 구조

**MSA로 갈라질 수 있는 상태로 만듭니다.** 지금은 한 프로젝트 안의 여러 모듈이지만, 프로세스를 나눴을 때 **실제로 나뉘어야** 합니다.

이 형태를 **모듈러 모놀리스**라고 부릅니다. 처음부터 쪼개지 않고 **쪼갤 수 있게** 만듭니다.

```
hanumoka-be/
├── app/                 조립 — 프로세스가 되는 자리
│   └── app-monolith        main · WAS · 환경 설정. 도메인은 없다
│
├── platform/            여러 서비스가 함께 쓰는 기반
│   ├── platform-event      메시지 브로커, Outbox
│   ├── platform-lock       분산락
│   └── platform-cache      캐싱
│
├── contract/            서비스 사이의 계약 (이벤트 스키마)
│
└── service/             독립 배포 단위
    ├── service-order       주문. 자기 DB
    └── service-inventory   재고. 자기 DB
```

`platform/`과 `contract/`는 **아직 없습니다.** 쓰기 시작할 때 만듭니다.

### `app` 층이 따로 있는 이유

**기동되는 모듈은 하나입니다. 다만 그 하나를 도메인 모듈이 겸하지 않습니다.**

겸하면 부팅하려고 다른 도메인을 classpath에 갖고 있어야 하고, 그러면 **규칙 1이 빌드 파일에서 되살아납니다.**
`service-order`가 부팅 모듈인 한 `service-inventory` 의존을 지울 수 없어, 이벤트로 바꿔도 그 줄이 남습니다.

**프로세스를 가르면 이 층이 늘어납니다.** 그때 `service`·`platform` 코드는 한 줄도 안 바뀝니다 — 그것이 이 분리가 사려는 값입니다.

| 모듈 | Boot 플러그인 | `main` | 산출물 |
|---|---|---|---|
| `app/*` | 적용 | 있음 | 실행 가능 jar |
| `service/*` · `platform/*` | 없음 | 없음 | 라이브러리 jar |

### 지키는 규칙 다섯

이걸 어기면 나중에 갈라지지 않습니다.

1. **`service`끼리 서로의 클래스를 직접 부르지 않습니다.** 이벤트로만 대화합니다.
2. **`service`는 자기 DB만 씁니다.** 서로의 테이블을 조인하지 않습니다.
3. **`service` → `platform` 방향만 있습니다.** 반대는 없습니다.
4. **`platform`은 도메인을 모릅니다.** 락이 「재고」를 아는 순간 재고 전용이 됩니다.
5. **`app`은 모두를 알고, 아무도 `app`을 모릅니다.** 도메인이 조립 지점을 알면 그 모듈은 이 프로세스 전용이 됩니다.

★ **0단계는 규칙 1을 일부러 어긴 채로 시작합니다.** `service-order`가 `service-inventory`를 직접 부릅니다.
비교할 기준선을 먼저 만드는 것이 목적이고, 1단계에서 이벤트로 바꾸며 해소합니다.
`service-order/build.gradle.kts`의 그 한 줄에 주석으로 표시해 두었습니다.

## 시나리오

**주문이 생기면 재고를 깎습니다.** 이것 하나로 여러 모듈을 관통합니다.

시나리오가 복잡하면 정작 보려는 것이 안 보입니다. **단순한 도메인에 어려운 보장 문제**를 놓았습니다.

- 같은 주문 이벤트가 두 번 오면 재고가 두 번 깎이면 안 됩니다 → **멱등성**
- 같은 상품의 이벤트는 순서가 지켜져야 합니다 → **파티션 키**
- 주문 저장과 이벤트 발행은 하나로 묶이지 않습니다 → **Outbox**
- 재고 차감의 동시성 → **분산락**
- 재고 조회 → **캐싱**

## 모듈 순서

| 순서 | 모듈 | 층 |
|---|---|---|
| 1 | 이벤트 시스템 + 측정 기반 | `platform-event` + `service-order` + `service-inventory` |
| 2 | 분산락 | `platform-lock` |
| 3 | 캐싱 | `platform-cache` |
| 4 | 계정계 | `service-account` |

## 모듈 하나가 끝났다는 것

넷을 다 채워야 끝입니다.

| | |
|---|---|
| **동작** | 코드가 돌고 테스트가 있다 |
| **근거** | 왜 이렇게 만들었는지, 무엇을 버렸는지가 `README.md`에 있다 |
| **측정** | 처리량·지연·병목과 측정 조건이 `MEASUREMENT.md`에 있다 |
| **설명** | 아무것도 보지 않고 10분 설명할 수 있다 |

**넷째가 안 되면 나머지가 다 돼도 끝난 것이 아닙니다.**

## 현재 상태

**0단계 진행 중 — 골격이 서고 프로세스가 뜹니다. 도메인은 아직 비어 있습니다.**

0단계는 이벤트 없이 만듭니다 — 한 프로세스에서 주문을 저장하고 재고를 깎습니다. **비교할 기준선을 먼저 만드는 것이 목적**이라 브로커는 아직 쓰지 않습니다.

| | 상태 |
|---|---|
| 3층 골격 (`app` · `service` 둘) | 섰습니다 |
| 프로세스 기동 · HTTP · JSON 왕복 | 됩니다. `SmokeController`와 그 테스트가 근거입니다 |
| 주문·재고 도메인, MySQL, JPA | **아직 없습니다** |
| 관측성 · 측정 | **아직 없습니다** |

`SmokeController`는 배관만 확인하는 임시 코드입니다. **첫 실제 도메인 엔드포인트가 생기면 지웁니다.**

## 실행

```bash
./gradlew build                    # 컴파일 + 테스트
./gradlew :app:app-monolith:bootRun
curl -X POST localhost:8080/smoke/items -H 'Content-Type: application/json' -d '{"name":"keyboard"}'
```

**JDK 25가 필요합니다.** `jvmToolchain(25)`은 「25 이상」이 아니라 **정확히 25**를 찾습니다 — 26이 설치돼 있어도 대신 쓰지 않습니다.
